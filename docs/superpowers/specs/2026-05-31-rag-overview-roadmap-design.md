## 0. 本文档的定位

本文档是**总览（overview）spec**，目的是把整套规范 RAG 系统拆成若干**独立子项目（里程碑 M0–M9）**，定义它们的范围、交付物、验收标准、依赖关系、子系统间接口与风险。

它**不**包含任何里程碑的代码级实现细节——每个里程碑后续各自走自己的 `spec → plan → 实现` 循环。本文档是这些子项目的总纲与排期依据。

**约束背景（决定了排序与拆分边界）：**
- 单人开发；
- 第一阶段 MVP 目标周期：几周；
- MinerU 解析服务当前**没有**，需在第一阶段（M2）部署；第一阶段同时落地 poppler 与 MinerU；
- 开发机：Windows + VS2022 + vcpkg。

---

## 1. 组织原则：walking skeleton 先行，再横向加厚

文档 §17 给出的是"横向五阶段"。本总览把它**重排为"先纵向打通一条最细的端到端线（walking skeleton），再逐层加厚"**。

- 文档的全部设计点一个不丢，只改变上线顺序；
- 价值：单人 + 绿地项目下，最大收益是**尽快拿到端到端信号**、尽早暴露 MinerU / Milvus / DeepSeek 溯源 / C++↔服务调用这类外部依赖的坑；同时契合文档 §15.1「评估必须前置」——有了端到端管道才谈得上评估；
- 代价：里程碑编号与文档阶段不再一一对应，故本文 §5 提供「文档章节 → 里程碑」映射表，保证不丢设计点。

## 2. 里程碑骨架（M0–M9）

每个里程碑 = 一个独立子项目。

| 里程碑 | 名称 | 对应文档阶段 |
|---|---|---|

| **M1** | **端到端最小骨架**：1 份原生 PDF → poppler 抽取 → 朴素条款切分 → 最小 PG 表 → 单路 dense 召回 → DeepSeek 带溯源回答 | §17.1 的纵切子集 |
| **M2** | 入库正规化 + 结构化底座加厚：条款层级树、原子条款/检索文本分离、page/clause 映射、表格结构化建表、**MinerU 接入（与 poppler 并行）** | §5 / §6 / §7 / §8.2 |
| **M3** | 文本路三路召回：查询理解前置（标准号/条款号归一化、分词/同义词词典）、dense+BM25+PG 精确、RRF 融合、状态+密级统一过滤 | §9.0 / §9.2 / §9.6 / §10.1 |
| **M4** | 评估闭环：100 条评估集、检索/生成指标、拒答阈值标定、数值后置校验 | §11.4 / §15 |

| **M6** | 版本管理与运维健壮性：版本状态流程、局部修订/修改单、PG↔Milvus 一致性、分级降级/延迟预算、embedding 灰度迁移 | §13 / §16.4 / §16.5 |
| **M7** | 视觉路试点（page 级）：poppler 渲染、page_visual、page→clause 映射 | §17.3 |
| **M8** | block 级视觉增强：page_blocks、block_visual、block→clause | §17.4 |
| **M9** | both 模式 + auto 路由：跨模态融合去重、auto 路由、both 评估 | §9.4 / §9.5 / §17.5 |

**第一阶段（文本路 MVP）= M0–M4**，poppler 与 MinerU 都在内。其中 **MinerU 部署（M2）位于关键路径，是第一阶段最大风险点**（见 §6）。

**M1 排在 M2 之前的理由**：M1 能在几天内给出第一个"能引用条款号的回答"，尽早暴露外部依赖坑。M1 用临时简化实现（朴素切分、最小表、单路召回），M2–M4 再替换为文档正规设计。

## 3. 各里程碑：范围 / 交付物 / 验收 / 依赖

### 3.1 第一阶段（M0–M4，详细）

#### M0 — 环境与依赖就绪
- **范围**：装好 PostgreSQL、Milvus（确认版本支持 §8.2 用到的稀疏向量 2.4+ / 全文检索 2.5 / 中文 JIEBA analyzer）、确认 DeepSeek API key；VS2022/vcpkg 编译通过 C++ 依赖链（poppler-cpp、libpqxx、libcurl 或 cpp-httplib、nlohmann/json、Milvus 访问方式、spdlog）。
- **交付物**：可编译运行的 C++ 骨架，含四个连通性冒烟测试（连 PG / 连 Milvus / 调通 DeepSeek 一次 / poppler 打开一个 PDF）。
- **验收**：四个冒烟测试全绿；Milvus 目标版本**显式验证**支持稀疏向量 + 全文检索 + JIEBA。
- **依赖**：无（起点）。

#### M1 — 端到端最小骨架（必达硬目标）
- **范围**：选 1 份原生 PDF，poppler 抽文本 → 朴素按条款号正则切分 → 写入最小 PG 表（standards + clause_nodes 子集）→ 调 embedding 生成 dense 向量写 Milvus → 单路 dense 召回 top-k → 组装上下文 → DeepSeek 输出带标准号/条款号的回答。
- **交付物**：命令行可跑通"入一篇 → 问一个 → 得到带溯源的答"。
- **验收**：对该文档问一个条款相关问题，回答能正确引用对应条款号。
- **依赖**：M0。
- **开放问题**：dense 向量用哪个 embedding（见 §7）。M1 用临时/API embedding 顶住，不阻塞。

#### M2 — 入库正规化 + 结构化底座加厚
- **范围**：将 M1 临时实现替换为文档正规设计——完整条款层级树（章/节/条/款/项）、`atomic_text` / `retrieval_text` / `context_text` 三文本分离（§7.2）、page_clause_map、表格结构化建表（spec_tables + spec_table_cells，§5.6）、解析质检与入库门禁（§14.1 / §14.2）；**接入 MinerU 服务并与 poppler 并行**（原生 PDF 走 poppler 快路，扫描/复杂表格走 MinerU）。
- **交付物**：完整文本路入库流程（§8.1 文本路部分）；一批文档能正确建出条款树与结构化表格。
- **验收**：抽样文档的条款号连续性、页码映射完整性、表格 cell 还原正确率达到质检门槛；MinerU 服务可被 C++ 调通。
- **依赖**：M1；**MinerU 部署（GPU）= 关键路径风险**。

#### M3 — 文本路三路召回
- **范围**：查询理解前置层（标准号/条款号解析归一化 §9.0.1、领域同义词词典 §9.0.2、中文自定义分词词典 §9.0.3）；dense + BM25 + PG 精确匹配三路（§9.2）；RRF 融合（§10.1）；**状态 + 密级统一过滤下推到 Milvus 标量与 PG**（§9.6，不可绕过）；small-to-big 回填（§10.4）。
- **交付物**：`text` 模式完整检索链路。
- **验收**：标准号/条款号精确查询稳定命中；状态过滤默认只回现行；密级过滤经 PG 二次校验；自定义分词词典已加载（BM25 上线前置硬条件）。
- **依赖**：M2。

#### M4 — 评估闭环
- **范围**：建 100 条评估集（§15.2 题型配比，含"应拒答"难例）；检索指标（recall@k、MRR、条款命中率…）与生成指标（条款引用准确率、废止误用率、数值单位准确率…）；拒答阈值在评估集上标定（§11.4）；数值后置校验模块（正则提数值与 PG 原文硬匹配）。
- **交付物**：一键跑评估出报告；拒答阈值有据可依。
- **验收**：评估脚本可重复运行；MVP 指标有 baseline 数字。
- **依赖**：M3。

### 3.2 后续阶段（M5–M9，粗粒度）

| 里程碑 | 范围要点 | 验收边界 | 依赖 |
|---|---|---|---|
| **M5 文本路增强** | 文本 reranker（top20→top5，§10.3）；表格 cell 级结构化定位（§9.7）；一跳引用图扩展回填（§10.5）；LLM 离线元数据增强（§12.4，后台不阻塞入库）；上下文 token 预算（§11.5） | 用 M4 评估集验证：reranker、引用扩展、cell 定位对"条款命中率/数值准确率"有正增益且不引入噪声 | M4 |
| **M6 版本管理与运维健壮性** | 版本状态流程（新增/改版/废止，§13.3）；局部修订/修改单条款级版本（§13.3）；PG↔Milvus 一致性对齐 + 查询时以 PG 为准（§13.4）；分级降级链 + 延迟预算 + 缓存（§16.4）；embedding 灰度迁移（§16.5） | 废止标准默认不召回；改版后旧版自动作废；任一外部服务挂掉有降级路径而非整体报错 | M3（部分可与 M5 并行） |

| **M8 block 级视觉增强** | page_blocks、block 裁剪、`block_visual`、block→clause 映射、block-level rerank | 视觉路条款定位精度优于 page 级 | M7 |

## 4. 子系统间接口约定（加厚不返工的关键）

walking skeleton 的核心风险是"M1 临时实现 → 后续替换正式实现时大返工"。规避办法：**先钉死接口，内部实现允许替换**。以下 5 个契约从 M1 起即生效。

**① 解析器接口（poppler 与 MinerU 可互换）**
抽象为"解析器"：输入文件，输出**统一中间格式**（文档标题、条款层级、正文文本、表格、公式、页码、block、OCR 置信度——§6.3）。M1 用 poppler 最小实现（仅文本+页码），M2 加 MinerU 完整实现。下游结构化处理模块只认中间格式，不关心解析来源。这是 M1→M2 不返工的关键。

**② Embedding 服务接口**
抽象为"文本→向量"，背后临时 embedding（M1）或 Qwen3-Embedding-8B（M5）对调用方透明；维度为配置项。配合 §16.5：换模型 = 换实现 + 新 collection 灰度，调用方不动。

**③ 检索器接口（单路→三路可叠加）**
每个召回源（dense / BM25 / PG 精确）实现同一"检索器"接口：输入归一化 query + 过滤条件，输出**带分数的候选列表**。M1 只挂 1 个 dense；M3 注册 BM25、PG 两个，RRF 在候选层融合。新增召回源 = 注册新检索器，融合逻辑不改。

**④ 候选归一化契约**
所有候选一律归一到 `standard_id + clause_id`（§10.2 去重键）。文本路、视觉路、引用扩展候选都用此键去重合并。M7/M9 视觉路与 both 模式靠它才能与文本路融合，故从 M1 即采用。

**⑤ 生成上下文契约**
注入 DeepSeek 的上下文固定为 §11.3 结构化片段（source_id / standard_no / clause_no / status / is_mandatory / text / tables…）。生成端 Prompt 与溯源校验只认此 schema；无论上游是 small-to-big、引用扩展还是表格 cell 注入，都往此结构填。

**底座原则（贯穿全程）**：Milvus 只负责召回，任何候选最终都要用 `clause_id` 回查 PG 拿权威字段（status、access_level、原文）；密级与版本以 PG 为准（§9.6 / §13.4）。从 M1 生效。

## 6. 风险与关键路径

**关键路径**：M0 → M1 → M2 → M3 → M4 串行（单人，难大幅并行）。

| 风险 | 影响里程碑 | 为什么危险 | 应对 |
|---|---|---|---|
| **MinerU 部署**（需 GPU、环境复杂） | M2，关键路径 | 第一阶段要做但当前没有；单人搭 GPU 推理服务最易超期 | M1 先用 poppler 打通端到端**不等 MinerU**；MinerU 作为 M2 独立任务，若卡住，M3/M4 仍可先用 poppler 的原生 PDF 子集推进 |
| **Milvus 版本特性** | M0 / M3 | §8.2 用到稀疏向量(2.4+)/全文检索(2.5)/中文 JIEBA analyzer，版本不对卡 BM25 | M0 冒烟测试显式验证目标版本支持这些特性 |
| **Embedding 选型未定** | M1 / M5 | Qwen3-Embedding-8B 需 GPU；不定临时方案 M1 动不了 | M1 用临时/API embedding（接口②隔离），正式模型推迟到 M5 灰度迁移 |
| **单人 + 几周做完 M0–M4 偏紧** | 全程 | M0–M4 含 MinerU 部署 + 完整三路召回 + 评估集，对单人几周乐观 | **M1 设为"必达"硬目标**；M2–M4 为"尽力"目标；时间紧时 M2 表格 cell 结构化、M4 完整评估可缩为最小子集先交付 |
| **中文分词词典缺位致 BM25 召回塌陷** | M3 | §9.0.3：不加自定义词典，标准号/术语被切碎 | M3 将"自定义分词词典 + 同义词词典"作为 BM25 上线前置硬条件 |

**预期管理**：M0–M4 完整版（含 MinerU + 完整评估闭环）对单人而言，"几周"更现实的形态是"M1 几天内出，M2–M4 数周滚动交付"。用"必达/尽力"分层管理，不假装全部按时做完。

## 7. 开放问题（需在对应里程碑前定夺）

1. **Embedding 模型选型**：M1 临时方案具体用什么（轻量本地 / 第三方 API）？正式 Qwen3-Embedding-8B 的 GPU 何时到位？— 在 M1 开工前定临时方案，M5 前定正式方案。
2. **Milvus 版本**：当前/计划安装的 Milvus 具体版本号？— 在 M0 确认。
3. **MinerU 部署形态**：本地 GPU 机 / 远程服务？GPU 资源何时可用？— 在 M2 开工前定。
4. **首批文档清单**：用于 M1/M2 的具体规范文件（原生 PDF 优先）。— 在 M1 前选定 1 份，M2 前选定一批。
