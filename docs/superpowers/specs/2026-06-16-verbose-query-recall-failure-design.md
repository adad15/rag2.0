# 啰嗦查询召回失败问题（诊断）

- 日期：2026-06-16
- 类型：问题诊断 spec（自然语言整句导致 dense+bm25 两路同病的召回失败）
- 来源：2026-06-16 用 `retrievecheck` 诊断"哪些混凝土试验用到天平"召回失败；推翻 memory `bm25-suspected-broken` 的旧假设
- 分支：V3.1
- 状态：**问题已诊断确认（有证据）；修复方案待定，本文档暂不展开**
- 背景：M3b 上线 BM25 关键词路后，本以为三路召回能覆盖"列举类"问题，但实测一个典型问题召回全错。memory 当时怀疑"BM25 没生效"，本次用 `retrievecheck` 做了对照实验，证明 BM25 本身正常，真正病因是**查询表述**，且 dense 路同病。

---

## 1. 一句话问题

"哪些混凝土试验用到天平"这类**啰嗦的自然语言列举问题**召回全错：含答案的 chunk（各试验"2 仪具与材料"里写"天平…"的段）一条都进不了 top-k，召回的全是"总则/目的适用范围"这类泛 chunk。

---

## 2. 问题诊断

### 2.1 现象

用户问：`公路工程水泥及水泥混凝土试验规程中哪些混凝土试验用到了天平`，期望召回各试验"2 仪具与材料"里含"天平 量程5kg 感量1g"的 chunk。实际 `retrievecheck …20` 召回的 20 条**全是**两类泛 chunk：

- `1.0.x 总则`（为规范……制定本规程 / 本规程适用于……）
- 各试验`第1节 目的、适用范围和引用标准`（本方法规定了水泥混凝土……试验方法）

含"天平"的 chunk 一条都没进 top 20。库里实有 27 个含天平 chunk、分属 24 个试验，数据齐全（chunk_cache `5797633264338373449.json`）。

### 2.2 根因

数据流（[`text_retrieve`](../../../src/retrieve/text_search.cpp)）把**整句原样**喂进两路：

- [`analyze_query`](../../../src/query/query_analysis.cpp) 里 `a.clean_text = question;`——只用正则抽了标准号/条款号/方法号，**没做任何关键词抽取或停用词过滤**。
- [`Bm25Retriever`](../../../src/retrieve/bm25_retriever.cpp) 把整句（经同义词扩展后）交给 Milvus 全文检索；[`DenseRetriever`] 把整句 embedding 去做余弦。

于是整句被 jieba 切成约 `公路 / 工程 / 水泥 / 水泥 / 混凝土 / 试验 / 规程 / 中 / 哪些 / 混凝土 / 试验 / 用到 / 了 / 天平`：

- **BM25 侧**：满库词（水泥/混凝土/试验/规程）在每个泛开篇 chunk 里反复命中，BM25 对查询各词的贡献求和；泛 chunk 命中词多、且短文档被长度归一化（参数 `b`）加成，累加分**压过**只命中"天平"一个词的长"仪具"chunk。在这个**单一领域语料**里满库词 IDF 压制不足，是关键放大器。
- **dense 侧**：整句"水泥混凝土试验规程"的语义最接近同样啰嗦的"总则/概述"句，所以 dense 也返回泛 chunk。
- [`build_text_collection_body`](../../../src/milvus/milvus_rest.cpp) 的 analyzer 只有 jieba 分词、**无 `stop` 停用词过滤**，虚词/满库词全部进索引与查询，无人去噪。

**结论：这是查询表述导致的 dense+bm25 两路同病的召回失败，不是 BM25 索引故障。**

### 2.3 证据（对照实验，同一套三路召回 + RRF，只改查询词）

| 查询 | 融合后 top 结果 |
|---|---|
| `天平` | ✅ 全是"仪具与材料"chunk（含纯 `bm25` 命中） |
| `混凝土试验天平` | ✅ 7 条全是"仪具与材料" |
| `天平 仪具` | ✅ 全是"仪具与材料" |
| `哪些试验用到天平` | ⚠️ 前 2 条对，后面跑偏 |
| 原始整句 | ❌ 20 条全是泛开篇 chunk |

**结果质量与查询里"满库词/虚词"的载荷成反比**——这直接证明：

1. BM25 能正确分出并匹配"天平"（它甚至不在 `config/user_dict.txt`），**推翻 memory 假设①"jieba/全文索引没生效"**，以及"dict 缺 `_default_`"的担忧；
2. 真因是 memory 假设②**词频污染**；
3. 把查询裁成关键词后两路立刻都对，说明修复着力点在**查询侧**，而非 BM25 索引。

---

## 3. 影响

- **列举/聚合类问题**（"哪些…用到…""有哪些试验需要…"）整类召回失败——这类问题恰恰最依赖稀有判别词，最易被啰嗦句式淹没。
- 因为是**两路同病**，单独修 BM25 或单独修 dense 都不彻底；评估时需把两路一起看。
- "修好"的判定（与具体方案无关）：同一个原始整句问题的召回里，能出现**多个不同 method_no 的"2 仪具与材料"含天平 chunk**；同时 §2.3 的短查询不回归、普通非列举问题召回不变差。
