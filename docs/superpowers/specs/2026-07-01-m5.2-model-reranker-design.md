# M5.2 ModelReranker Design

## Goal

Add a model-based reranker for the text retrieval path, using SiliconFlow's `Qwen/Qwen3-Reranker-8B` as the target model. The feature must support `RAG_RERANK_MODE=model` and `RAG_RERANK_MODE=hybrid`, keep the existing `off` and `light` behavior intact, and fail closed to deterministic local ranking when the model call cannot be trusted.

## Current Context

M5.1 introduced the reranker framework:

- `RerankParams`, `RerankCandidate`, `IReranker`, and `LightReranker` live in `src/retrieve/reranker.h`.
- `light_rerank` and `build_rerank_candidates` live in `src/retrieve/reranker.cpp`.
- `text_retrieve` applies rerank only for non-list queries. List-by-condition queries still use the key-term coverage path.
- Commit `86dea58` added a safety valve: if PostgreSQL candidate lookup returns an empty rerank pool, the pipeline falls back to the original RRF order.

The workspace also contains old unrelated uncommitted changes. M5.2 changes must be scoped to reranker/API/config/tests/docs and must not stage unrelated files.

## API Client Boundary

Do not reuse `DeepSeekClient` directly for reranking.

`DeepSeekClient` is a chat-completions client in the generation layer:

- Input shape: `system + user`.
- Output shape: `choices[0].message.content`.
- Namespace and error messages are generation-oriented.

`Qwen/Qwen3-Reranker-8B` is a dedicated reranker. Its application shape is query-document scoring:

- Input shape: query plus candidate documents.
- Output shape: scored document results.

M5.2 should add a retrieval-layer client, tentatively named `RerankApiClient`, under `src/retrieve/`. It should reuse the existing `http::post_json` infrastructure, but it should not depend on or extend `DeepSeekClient`.

## Configuration

Add rerank-specific config fields:

- `RAG_RERANK_BASE_URL`, default `https://api.siliconflow.cn`
- `RAG_RERANK_PATH`, default `/v1/rerank`
- `RAG_RERANK_MODEL`, default `Qwen/Qwen3-Reranker-8B`
- `RAG_RERANK_KEY`, default empty
- `RAG_RERANK_TIMEOUT_SEC`, default `20`

`RAG_RERANK_KEY` should fall back to `RAG_DEEPSEEK_KEY` when empty so local configs can opt into rerank without duplicating the same provider key. The model name should stay independently configurable.

Existing fields remain:

- `RAG_RERANK_MODE=off|light|model|hybrid`
- `RAG_RERANK_POOL_MULT`
- `RAG_RERANK_MAX_PER_CLAUSE`

## Rerank Input

`ModelReranker` should receive the same `QueryAnalysis`, rerank pool, and `top_k` as `LightReranker`.

Each `RerankCandidate` should be converted into a compact document string. The document text should include the strongest retrieval signals without dumping excessive context:

- title
- path text
- clause number and method number when present
- atomic text
- short context text or BM25 text as supporting content

Candidate order must preserve the original RRF order before model scoring so fallback and tie behavior are stable.

## Rerank Output

`RerankApiClient` should parse scored results into a simple internal result shape:

- candidate index
- score

The parser must reject responses that are not structurally usable. A usable response must contain at least one valid index that maps back to the current candidate pool.

`ModelReranker` should:

- sort valid scored candidates by descending score;
- ignore duplicate or out-of-range indexes;
- append candidates omitted by the model in original RRF order;
- truncate to `top_k`;
- preserve deterministic behavior for ties.

## Mode Semantics

`off`:

- No rerank. Keep current RRF behavior.

`light`:

- Keep current LightReranker behavior.

`model`:

- Build a rerank pool using PostgreSQL lookup.
- If the pool is empty, return the M5.1 RRF fallback.
- If the model call succeeds and returns usable scores, use model order.
- If the model call fails, times out, or returns unusable output, fall back to original RRF order.

`hybrid`:

- Build a rerank pool using PostgreSQL lookup.
- If the pool is empty, return the M5.1 RRF fallback.
- If the model call succeeds and returns usable scores, use model order.
- If the model call fails, times out, or returns unusable output, fall back to `LightReranker`.

List-by-condition queries:

- Do not enter model rerank in M5.2.
- Keep the existing keyword coverage and demotion path.

Clause and method pinning:

- Keep the existing exact pinning after rerank so explicit method/clause lookups remain protected.

## Error Handling

The model path must treat these as fallback cases:

- HTTP failure or non-2xx status.
- Request timeout.
- JSON parse failure.
- Response without usable scored results.
- All returned indexes out of range.
- Empty rerank pool after PostgreSQL lookup.

Fallback should be logged with enough detail to diagnose which branch was taken, but logs must not include API keys.

## Testing

Use TDD for implementation.

Unit tests should cover:

- config defaults and overrides for rerank API fields;
- rerank API request body construction;
- rerank API response parsing for valid scores;
- parser rejection for malformed or empty responses;
- `ModelReranker` model-order success path;
- duplicate/out-of-range index filtering;
- omitted candidates appended in RRF order;
- `model` failure fallback to RRF;
- `hybrid` failure fallback to `LightReranker`;
- empty pool fallback to RRF.

Integration-level verification should include:

- MSBuild test project;
- focused doctest for reranker/config tests;
- full doctest suite.

## Evaluation

After implementation, run rich eval across:

- `off`
- `light`
- `model`
- `hybrid`

Use the existing eval command shape:

```powershell
rag2.exe eval eval/retrieval_questions_100.annotated.json 30 rule --rich
```

Run each mode by changing `RAG_RERANK_MODE` in config or the local environment used by the executable.

Default strategy should be chosen from the rich eval output. Keep `off` as default unless `model` or `hybrid` improves ranking risk without hurting recall/complete metrics. The decision should consider:

- Group Recall and Complete;
- nDCG;
- Redundancy;
- Distractor Hit;
- Distractor-before-gold.

## Non-Goals

M5.2 does not add table cell localization, citation graph expansion, LLM metadata extraction, or model rerank for list-by-condition coverage queries.
