# M5.2 ModelReranker 设计

## 目标

M5.2 给文本检索链路加一个模型重排层。目标模型是硅基流动的 `Qwen/Qwen3-Reranker-8B`。

这次只处理 reranker 本身：支持 `RAG_RERANK_MODE=model` 和 `RAG_RERANK_MODE=hybrid`，保留 `off`、`light` 的现有行为。模型调用失败、超时或返回内容不可用时，系统必须回到确定性的本地排序，不能把不可信结果继续传下去。

## 当前上下文

M5.1 已经把 reranker 的基础结构搭好了：

- `src/retrieve/reranker.h` 里有 `RerankParams`、`RerankCandidate`、`IReranker` 和 `LightReranker`。
- `src/retrieve/reranker.cpp` 里有 `light_rerank` 和 `build_rerank_candidates`。
- `text_retrieve` 只在非列举题上做 rerank。列举题仍走关键词覆盖链路。
- `86dea58` 加了安全阀：PG 回查不到 rerank pool 时，直接回退 RRF 原顺序。

工作区里还有一些旧的未提交改动。M5.2 只改 reranker、API client、配置、测试和必要文档，不能把无关文件带进提交。

## API client 边界

不直接复用 `DeepSeekClient` 做 rerank。

原因是职责不同。`DeepSeekClient` 是生成层的 chat-completions client：

- 输入是 `system + user`。
- 输出取 `choices[0].message.content`。
- 命名空间、错误信息和调用语义都偏问答生成。

`Qwen/Qwen3-Reranker-8B` 是专用重排模型，调用语义是 query-document scoring：

- 输入是查询和候选文档列表。
- 输出是每个候选的索引和分数。

M5.2 新增一个 retrieval 层 client，暂定名 `RerankApiClient`，放在 `src/retrieve/`。它复用现有的 `http::post_json`，但不继承、不包装 `DeepSeekClient`。

### 确认的 API 契约（2026-07-01 核实硅基流动官方文档）

`POST /v1/rerank`，`Authorization: Bearer <key>`。只用文本变体（classic）。

请求体：

- `model`：`RAG_RERANK_MODEL`；
- `query`：查询文本（见输入构造）；
- `documents`：候选文档文本数组，保持 RRF 原顺序；
- `instruction`：任务指令，Qwen/Qwen3-Reranker 专属字段（见配置）；
- `return_documents`：`false`——靠 index 回映候选，不需要模型回传正文，省 token；
- 不传 `top_n`——让模型给整池打分并全部返回，漏排由本地补尾判定，而不是被服务端提前截断。

`max_chunks_per_doc` 和 `overlap_tokens` 只对 BAAI/网易有道模型有效，对 Qwen 无效，不使用。含义：**服务端不会自动切分长文档**，所以输入构造里的单 document 长度上限是唯一的长度闸。

响应体：

```json
{
  "id": "...",
  "results": [ { "index": 0, "relevance_score": 0.98 } ],
  "meta": { "tokens": { "input_tokens": 0 } }
}
```

- 分数字段名是 **`relevance_score`**，不是 `score`；解析器按这个名字取分。
- `index` 是**我们发送的 `documents` 数组下标**，直接回映到当前候选池。

## 配置

新增 rerank 专用配置：

- `RAG_RERANK_BASE_URL`，默认 `https://api.siliconflow.cn`
- `RAG_RERANK_PATH`，默认 `/v1/rerank`
- `RAG_RERANK_MODEL`，默认 `Qwen/Qwen3-Reranker-8B`
- `RAG_RERANK_KEY`，默认空
- `RAG_RERANK_TIMEOUT_SEC`，默认 `20`
- `RAG_RERANK_INSTRUCTION`，默认给一条公路规范域指令，例如“检索与给定查询最相关的公路工程标准规范条款或试验方法片段”。留空则请求不带 `instruction` 字段，退回模型默认行为。

`RAG_RERANK_KEY` 为空时回退到 `RAG_DEEPSEEK_KEY`。这样本地如果同用一个供应商 key，不用重复写；模型名仍然独立配置。

现有配置继续保留：

- `RAG_RERANK_MODE=off|light|model|hybrid`
- `RAG_RERANK_POOL_MULT`
- `RAG_RERANK_MAX_PER_CLAUSE`——统一的同条款多样性上限，默认 2。它对 `light`、模型调用成功后的 `model`/`hybrid` 输出，以及 `hybrid` 的 Light fallback 生效；`model` 模式失败回退 RRF 时不生效，保持“RRF 原顺序”语义。

## 输入构造

`ModelReranker` 和 `LightReranker` 使用同一套入口：`QueryAnalysis`、`RerankCandidate` pool 和 `top_k`。

每个 `RerankCandidate` 会转成一段紧凑的 document 文本。默认文本必须以规范正文为主，不把检索过程里的辅助材料都塞给模型。reranker 要判断的是“这个候选片段本身能不能回答问题”，冗余上下文会放大关键词噪声，反而可能把弱相关 chunk 排上来。

默认格式：

```text
标题: <title>
编号: 条款 <clause_no>；方法 <method_no>
正文: <atomic_text>
```

字段规则：

- `atomic_text` 是主体，必须优先使用；
- `title` 只作为短定位信息，帮助模型理解“本方法”“本节”指什么；
- `clause_no`、`method_no` 只在非空时写入；
- `path_text` 默认不写入，除非后续评估证明标题和正文不足以区分章节；
- `context_text` 默认不写入。只有当 `atomic_text` 很短，例如少于 80 个中文字符时，才补一小段，建议截断到 150-300 个中文字符；
- `bm25_text` 默认不写入，它更像检索辅助文本，容易带入重复关键词和召回噪声。

单个 document 要做长度上限控制，建议先按 800-1200 个中文字符处理。超长正文截断时保留开头即可，不做摘要。

候选顺序保持 RRF 原顺序。这样模型漏排、平分或失败时，都有稳定的本地顺序兜底。

`instruction` 不是 document 文本的一部分，而是请求体的独立字段，由 `RAG_RERANK_INSTRUCTION` 提供，对整批候选共用一次。document 文本仍然只含标题、编号、正文，不塞任务指令。

## 输出处理

`RerankApiClient` 把模型响应解析成内部结果：

- candidate index（= 发送数组下标）；
- score（取自响应的 `relevance_score` 字段）。

解析器只接受结构可用的响应。至少要有一个 index 能映射回当前候选池，否则视为失败。

`ModelReranker` 的排序规则：

- 有效候选按 score 降序；
- 重复 index 只保留第一次；
- 越界 index 直接忽略；
- 模型没返回的候选按原 RRF 顺序补到后面；
- 之后应用 `RAG_RERANK_MAX_PER_CLAUSE` 多样性后处理：同一个 `standard_id|clause_no` 超过上限的候选降到队尾；
- 最后截断到 `top_k`；
- 分数相同时保持稳定顺序。

pinning 不在 `ModelReranker` 内做，仍由 `text_retrieve` 在 rerank 之后统一执行。

## 缓存

rerank 打分结果落盘缓存，与标注、答案缓存同一套纪律，让 eval 可以重跑确定、省 token 和费用。

- 缓存键 = `model` + `instruction` + `query` + 候选 `chunk_id` 有序集 + document 构造版本号。任一变化即视为 miss。
- 候选集用 `chunk_id` 排序后入键，缓存值按 `chunk_id → relevance_score` 存。这样上游 ANN 跨次微漂移只改候选顺序、不改集合时，仍然命中；应用分数时按 `chunk_id` 匹配，与发送顺序无关。
- document 构造版本号是一个常量。改了输入构造格式就 bump 它，避免复用按旧格式算出来的分数。
- **去重、截断、pinning 都在缓存之外做。** 因此调 `RAG_RERANK_MAX_PER_CLAUSE` 或改 pinning 逻辑重跑 eval，不需要重打 API。
- 只有拿到可用打分才写缓存。模型失败、超时、非法响应一律不写（下轮重试）。
- 缓存目录沿用 `data/` 下惯例，例如 `data/rerank_cache/`。

## 装配与多态

`text_retrieve` 走 `IReranker` 多态，不堆 `if(mode)` 分支：

- `LightReranker`（已有）；
- `ModelReranker`：持有 `RerankApiClient` 和一个**兜底 `IReranker`**。模型成功用模型排序；失败、超时或非法响应走兜底；
- `model` 模式 = `ModelReranker{ 兜底 = RRF 透传 }`；
- `hybrid` 模式 = `ModelReranker{ 兜底 = LightReranker }`。

网络调用、超时、回退全部封在 `ModelReranker` 内部。`text_retrieve` 只按 mode 造对象、调一次 `rerank(qa, pool, top_k)`，保持薄。PG 回查构造 pool、pool 为空回退 RRF 这一层留在 `text_retrieve` 外层不变，与 M5.1 一致。

## 多样性后处理

把“clause 去重 + 超额降尾 + 截断 `top_k`”从 `light_rerank` 内部抽出来，做成确定性后处理：

- `light` 输出、模型调用成功后的 `model`/`hybrid` 输出都过同一道；
- `hybrid` 失败后回退到 `LightReranker`，因此也会走这道后处理；
- `model` 失败后回退 RRF 原顺序，不走这道后处理，避免“模型不可用”时额外改变 `off` 行为；
- 规则不变：同 `standard_id|clause_no` 出现超过 `max_per_clause` 的降到队尾，`clause_no` 为空的候选不受限，最后截断 `top_k`；
- `max_per_clause` 是统一配置，默认 2。`model` 模式的松紧（2 / 更大 / 0 表示不掐）由 rich eval 决定，不在设计阶段写死；
- 抽成独立后处理还有一个好处：它在缓存之外，扫这个参数重跑 eval 零 API 成本。

## 模式语义

`off`：不做 rerank，保持当前 RRF 行为。

`light`：保持 M5.1 的 LightReranker 行为。

`model`：

- 先用 PG 回查构造 rerank pool；
- pool 为空时走 M5.1 的 RRF fallback；
- 模型调用成功且返回可用分数时，使用模型排序；
- 模型排序后应用 `RAG_RERANK_MAX_PER_CLAUSE` 多样性后处理；
- 模型失败、超时或返回非法内容时，回退 RRF 原顺序。

`hybrid`：

- 先用 PG 回查构造 rerank pool；
- pool 为空时走 M5.1 的 RRF fallback；
- 模型调用成功且返回可用分数时，使用模型排序；
- 模型排序后应用 `RAG_RERANK_MAX_PER_CLAUSE` 多样性后处理；
- 模型失败、超时或返回非法内容时，回退 LightReranker。

列举题不进入 M5.2 的模型 rerank，继续走现有关键词覆盖和下压逻辑。

条款号、方法号 pinning 仍放在 rerank 和多样性后处理之后执行。显式查条款或方法号时，精确命中仍然优先。

## 错误处理

以下情况都走 fallback：

- HTTP 失败或非 2xx；
- 请求超时；
- JSON 解析失败；
- 响应里没有可用 scored result；
- 返回的 index 全部越界；
- PG 回查后的 rerank pool 为空。

进入 fallback 时不写缓存。日志要能看出进入了哪条 fallback 分支，但不能打印 API key。

## 评估

实现完成后跑 rich eval，对比四种模式：

- `off`
- `light`
- `model`
- `hybrid`

命令沿用现有形态：

```powershell
rag2.exe eval eval/retrieval_questions_100.annotated.json 30 rule --rich
```

每次切换 `RAG_RERANK_MODE` 后跑一遍。有缓存后，重跑同一模式确定且几乎零成本；扫 `RAG_RERANK_MAX_PER_CLAUSE` 也不需要重打 API。

默认策略根据 rich eval 决定。除非 `model` 或 `hybrid` 明显降低排序风险，且不伤 recall/complete，否则默认仍保持 `off`。主要看这些指标：

- Group Recall 和 Complete；
- nDCG；
- Redundancy；
- Distractor Hit；
- Distractor-before-gold。

M5.2 不做表格 cell 定位、引用图扩展、LLM 元数据抽取，也不把模型 rerank 接到列举题覆盖链路里。
