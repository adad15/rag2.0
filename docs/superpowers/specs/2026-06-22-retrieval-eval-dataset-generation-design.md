# 工程规范 RAG 召回评测集生成与评估设计

- 日期：2026-06-22
- 类型：检索侧评测增强设计
- 适用范围：工程规范、试验规程知识库（当前少于 10 份规范）
- 状态：设计已确认，待编写实施计划
- 前置能力：稳定的 `chunk_id`、标准号与版本、条款号、方法号、标题、正文、页码及结构树；现有 `rag2 eval` 已支持基础点查、覆盖查、`hit@k`、`MRR` 和 `coverage@k`

---

## 1. 目标

建立一套不依赖真实用户日志的检索评测闭环：

1. 从规范内容和结构化元数据反向生成评测问题。
2. 将每道问题绑定到稳定、可审计的必要证据，而非仅绑定一段参考答案。
3. 覆盖工程规范用户可能提出的多种问题，不局限于条款点查和方法列举。
4. 使用自动校验淘汰歧义题和错误金标，再由领域专家分层抽检 50～100 条。
5. 分别衡量“是否召回过相关内容”“必要证据是否全部召回”以及“错误干扰项是否被排到前面”。
6. 形成可冻结、可版本化、可用于检索调参与回归测试的数据集。

本阶段只评估检索层，不评价 LLM 最终答案，不修改现有召回逻辑。

---

## 2. 核心原则

### 2.1 先确定证据，再生成问题

评测样本必须采用“证据驱动”流程：

```text
规范结构与 chunk
    → 选择目标证据
    → 组装证据包
    → 生成问题与参考答案
    → 独立自动校验
    → 专家抽检
```

禁止先生成问题，再调用当前检索器寻找金标。否则评测集会继承当前检索器的偏差，漏召回内容可能永远不会进入 gold。

### 2.2 金标描述证据集合，不只描述单个 chunk

工程问题可能需要仪器、步骤、参数、适用条件等多处证据。评测集必须支持：

- 单 chunk 必要证据；
- 多个 chunk 共同构成完整答案；
- 多个等价 chunk 命中任意一个即可；
- 相关但非必要的补充证据；
- 高度相似但结论错误的干扰证据；
- 知识库无法回答的问题。

### 2.3 总分只用于概览，诊断依赖分层报告

相同总分可能来自完全不同的缺陷。所有指标必须按以下维度切分：

- 查询类型；
- 难度；
- 规范；
- 单证据/多证据；
- 正常表达/语言扰动；
- 正例/不可回答负例；
- 表格、公式、正文等证据形态。

### 2.4 自动生成不等于自动可信

LLM 负责提高问题多样性，但不能单独决定金标。金标必须来自结构化证据锚点，并经过规则检查、独立模型复核和专家抽检。

## 3. 方案选择

### 3.1 纯规则生成

根据条款号、方法号和标题套模板生成问题。

- 优点：金标准确、成本低、容易复现。
- 缺点：问题机械，主要测试精确匹配，无法充分覆盖口语化、条件推理和多证据查询。

### 3.2 纯 LLM 生成

让模型阅读 chunk 后直接生成问题与答案。

- 优点：题型和表达丰富。
- 缺点：容易产生证据不充分、题意歧义、答案越界和金标遗漏。

### 3.3 规则锚定 + LLM 改写 + 自动反查校验

先由规则选择稳定证据，再由 LLM 生成和改写问题，最后由独立校验流程验证问题与金标。

本项目采用该方案。它保留规则金标的可靠性，同时获得接近真实用户表达的查询多样性。

---

## 4. 首版数据规模

当前知识库少于 10 份规范，首版采用以下规模：

| 阶段 | 数量 | 说明 |
|---|---:|---|
| 原始候选 | 约 400 条 | 从不同规范、章节和证据形态分层生成 |
| 自动校验后 | 约 250～300 条 | 淘汰重复、歧义、越界和证据不充分样本 |
| 专家抽检 | 50～100 条 | 按题型、难度和规范分层抽样 |
| 冻结测试集 | 由抽检结果决定 | 抽检代表的批次通过质量门槛后冻结；逐条已审核样本保留独立标记 |

数据集扩大应由新增规范、失败案例和未来真实查询驱动，不在首版盲目扩充到数千条。

## 5. 查询类型矩阵

首版约 400 条候选题按以下比例生成：

| 查询类型 | 比例 | 主要检验能力 | 示例 |
|---|---:|---|---|
| 条款/方法定位 | 15% | 编号解析、精确路、版本过滤 | `T0521 需要哪些仪具？` |
| 单点事实 | 20% | 语义召回、关键事实定位 | `该试验的养护温度是多少？` |
| 操作步骤 | 15% | 程序性内容召回、顺序信息 | `混凝土试件应如何制作？` |
| 条件与适用范围 | 15% | 条件、例外、前提召回 | `什么情况下需要进行复检？` |
| 参数、公式、表格 | 10% | 数值、单位、公式和表格定位 | `加载速率如何确定？` |
| 比较与区别 | 10% | 多对象和多证据召回 | `两种检测方法有什么区别？` |
| 多证据汇总 | 10% | 必要证据完整性 | `完成该试验需要哪些设备和步骤？` |
| 跨条款/跨规范关联 | 5% | 多跳和跨文档检索 | `设计要求与试验方法分别依据什么？` |

### 5.1 难度

- `easy`：单个 chunk 足以回答，问题措辞接近原文。
- `medium`：单个或少量 chunk，包含口语化、简称或同义改写。
- `hard`：需要多个必要证据组、跨条款或跨规范，且存在相似干扰内容。

### 5.2 语言扰动

每类问题按需生成以下表达变体：

- 正式术语；
- 工程口语；
- 简称或省略标准号；
- 同义词替换；
- 带无关背景的长问题；
- 少量真实风格的错别字；
- 方法号、条款号的空格、连字符和年份格式变化。

同一事实最多保留两种问法，避免大量近重复样本抬高总分。

### 5.3 不可回答负例

约 10% 候选题设计为 `answerable=false`，包括：

- 规范中不存在的方法号或条款；
- 删除关键条件后无法唯一回答；
- 混合不同规范、不同试验的互斥条件；
- 询问规范未规定的参数或结论；
- 使用已废止版本提出与现行版本冲突的问题。

负例必须具有真实用户风格，不能用明显无意义文本充数。

## 6. 评测样本格式

建议将现有 `EvalCase` 扩展为以下逻辑模型：

```json
{
  "case_id": "eval-v1-000123",
  "question": "混凝土抗压强度试验需要哪些设备，加载速度是多少？",
  "query_type": "multi_evidence",
  "difficulty": "hard",
  "answerable": true,
  "language_variant": "colloquial",
  "source_standard_ids": ["standard_x"],
  "must_have_groups": [
    {
      "group_id": "equipment",
      "chunk_ids": ["chunk_equipment_1", "chunk_equipment_2"],
      "stable_refs": [
        {
          "standard_no": "JTG xxxx-xxxx",
          "method_no": "Txxxx-xxxx",
          "clause_no": "2"
        }
      ]
    },
    {
      "group_id": "loading_rate",
      "chunk_ids": ["chunk_loading_rate"],
      "stable_refs": [
        {
          "standard_no": "JTG xxxx-xxxx",
          "method_no": "Txxxx-xxxx",
          "clause_no": "5.3"
        }
      ]
    }
  ],
  "acceptable_chunks": ["chunk_parent_summary", "chunk_equivalent_table"],
  "distractor_chunks": ["chunk_similar_test"],
  "reference_answer": "供人工审核使用的简短答案",
  "generation": {
    "generator_version": "prompt-v1",
    "source_chunk_ids": ["chunk_equipment_1", "chunk_loading_rate"],
    "validation_status": "auto_pass",
    "expert_review": "unreviewed"
  }
}
```

### 6.1 字段语义

- `case_id`：评测样本稳定标识。
- `must_have_groups`：完整回答所需的证据组。每组中的多个 `chunk_ids` 表示等价证据，命中任意一个即可覆盖该组。
- `stable_refs`：标准号、方法号和条款号组成的持久定位。chunk 重建后可据此重新解析 ID。
- `acceptable_chunks`：相关且有帮助，但不是回答必需条件。
- `distractor_chunks`：与问题高度相似但对象、条件、版本或结论错误的已知干扰项。
- `reference_answer`：只用于生成质量校验和专家审核，不参与检索打分。
- `generation`：记录生成提示词版本、来源证据和审核状态，保证可追踪。

### 6.2 等价证据与共同必要证据

两个 chunk 可以有不同关系：

- 若任意一个都能独立支持同一事实，应放在同一个 `must_have_group`。
- 若两个 chunk 分别支持答案的不同部分，应放在不同 group。

这个区分直接决定 `Complete@k` 是否可信，不能仅因为 chunk 相邻就归为等价。

## 7. 数据生成流程

### 7.1 分层采样

按规范、章节、方法、正文、表格、公式和图示说明分层采样。每份规范设置最低样本配额，同时限制单一热门章节占比。

采样时排除：

- 正文过短且没有独立语义的 chunk；
- OCR 严重异常或 `suspect` 标记高风险的 chunk；
- 目录、页眉页脚等非知识正文；
- 缺少稳定定位字段且无法回溯原文的 chunk。

### 7.2 构建证据包

对目标 chunk 组装有限上下文：

- 当前 chunk；
- 父条款路径；
- 必要的子条款；
- 前后相邻 chunk；
- 显式引用的条款；
- 同一方法中的仪器、步骤、参数等相关段落；
- 对比较题或跨规范题所需的另一组证据。

证据包只包含生成该问题所需内容，避免把整本规范交给模型后难以确定真正的必要证据。

### 7.3 生成结构化草案

生成模型必须输出结构化 JSON：

- 问题；
- 查询类型；
- 难度；
- 可回答性；
- 必要证据组；
- 参考答案；
- 问题使用了哪些证据事实；
- 可能的相似干扰对象。

任何引用不到输入证据包的事实都视为越界并淘汰。

### 7.4 语言改写

对通过初筛的问题生成有限变体。改写不得：

- 改变事实条件；
- 删除区分相似试验所需的关键限定；
- 引入证据包外的新事实；
- 直接复制长段原文；
- 在问题中泄露答案。

### 7.5 自动反查校验

校验阶段与生成阶段使用不同提示词；条件允许时使用不同模型。校验器只查看问题和 gold 证据，不查看当前检索器结果，并判断：

1. 问题能否仅凭 gold 证据回答；
2. 每个必要证据组是否真正必要；
3. gold 是否遗漏关键证据；
4. 问题是否存在多个合理解释；
5. 参考答案中的参数、单位、编号和条件是否与原文一致；
6. 问题是否主要依赖外部常识；
7. 问题是否过度复制原文，导致检索过于容易；
8. 难度和查询类型标签是否合理。

校验输出 `pass`、`reject` 或 `needs_review`，并给出结构化原因。

### 7.6 干扰项发现

针对正例问题，从同一规范或相似方法中寻找：

- 标题相似但试验对象不同的 chunk；
- 参数名称相同但适用条件不同的 chunk；
- 同条款号但属于另一规范的 chunk；
- 同一方法的旧版本或废止版本；
- 共享仪器名称但并不回答问题的 chunk。

干扰项先由规则或 embedding 产生候选，再由校验模型确认其“相似但错误”属性。

### 7.7 去重

同时执行：

- 规范化文本后的精确去重；
- 基于问题 embedding 的近重复聚类；
- 按 gold 证据组去重；
- 限制同一事实和同一 chunk 的样本数量。

不能只按问题文本去重，否则同一证据可能被大量不同措辞重复采样。

---

## 8. 专家抽检

从自动通过的约 250～300 条样本中，分层抽检 50～100 条。

### 8.1 抽样优先级

优先检查：

- `hard` 难度；
- 多证据与跨规范题；
- 表格、公式和数值题；
- 不可回答负例；
- 校验器置信度较低或标为 `needs_review` 的题；
- 每份规范至少若干题，避免审核集中在单一文档。

### 8.2 审核项

领域专家只需确认：

- 问题表达是否自然；
- 知识库是否能够回答；
- 必要证据是否完整；
- 等价证据分组是否正确；
- 干扰项是否确实错误；
- 参考答案、参数和单位是否正确；
- 查询类型和难度是否基本合理。

### 8.3 质量门槛

抽检错误包括：不可回答、gold 缺失、gold 错误、关键条件错误、答案越界、负例实际可回答。

- 抽检错误率 `≤ 5%`：可冻结为测试集。
- 错误率 `> 5% 且 ≤ 10%`：修正规则或提示词后，对受影响类别重新生成并复检。
- 错误率 `> 10%`：整批不进入冻结集，必须重新生成。

错误率应同时按题型观察；即使总错误率合格，某一题型错误率过高也不能直接放行该类别。

## 9. 检索指标

设某样本有 `G` 个必要证据组，top-k 结果覆盖其中 `g` 个。

### 9.1 Group Recall@k

```text
Group Recall@k = g / G
```

它衡量必要证据召回了多少。单证据问题等价于传统 `Recall@k`/`Hit@k`。

### 9.2 Complete@k

```text
Complete@k = 1，当且仅当 g = G；否则为 0
```

数据集层面取样本平均值。它是本项目的核心指标，因为只召回部分证据往往不足以支持正确回答。

### 9.3 MRR

第一条必要证据出现排名的倒数；没有命中记 0。MRR 衡量用户或生成模型多久能看到第一条有效证据，但不能替代多证据完整率。

### 9.4 nDCG@k

用于衡量整体排序质量：

- 必要证据：高相关等级；
- `acceptable_chunks`：较低相关等级；
- 其他结果：0。

同一个必要证据组中的多个等价 chunk 应避免重复累积过高收益：该组首次命中获得主要收益，后续等价重复项降权或不再计增益。

首版采用明确的离散收益：

- 必要证据组首次命中：`2`；
- `acceptable_chunks` 首次命中：`1`；
- 同组等价证据的重复命中和其他结果：`0`。

理想排序按必要证据组在前、可接受证据在后构造，确保重复召回同一事实不会虚增 nDCG。

### 9.5 Distractor@k

```text
Distractor@k = 进入 top-k 的已知干扰项数 / 该样本已标注干扰项数
```

没有标注干扰项的样本不进入该指标分母。

同时报告：

- `Distractor Hit@k`：top-k 是否出现任一已知干扰项；
- `Distractor-before-gold`：干扰项是否排在首个必要证据之前。

### 9.6 Redundancy@k

统计 top-k 中来自同一必要证据组、同一方法或高度重复文本的结果占比，用于发现 top-k 被同义重复 chunk 占满、导致其他必要证据无法进入的问题。

### 9.7 不可回答问题

当前 RRF 分数不保证能跨查询直接比较，因此不能把固定 RRF 阈值直接称为“高置信度”。首版对 `answerable=false` 样本报告：

- top-k 中被人工或自动判定为貌似支持错误答案的结果比例；
- 已知伪相关干扰项的排名；
- top-1/top-3 是否出现可诱导错误回答的内容。

如果后续要实现检索拒答阈值，应先增加可跨查询校准的相关性分数或 reranker 分数，再单独评估阈值下的误接受率和误拒绝率。

### 9.8 k 值

统一报告：

```text
k ∈ {1, 3, 5, 10, 20}
```

这样既能观察最终上下文窗口常用的较小 k，也能区分“完全没有召回”与“召回了但排序靠后”。

## 10. 报告结构

每次评测至少输出：

### 10.1 总览

- 样本数；
- `Group Recall@1/3/5/10/20`；
- `Complete@1/3/5/10/20`；
- `MRR`；
- `nDCG@5/10/20`；
- `Distractor Hit@5/10/20`；
- `Redundancy@5/10/20`。

### 10.2 分层

- 按 `query_type`；
- 按 `difficulty`；
- 按 `standard_id`；
- 按单证据/多证据；
- 按 `language_variant`；
- 按正文/表格/公式；
- 按正例/不可回答负例。

### 10.3 失败清单

对每条失败样本打印或导出：

- 问题；
- 必要证据组；
- top-k 结果及排名；
- 召回来源（dense、BM25、exact 等）；
- 缺失的证据组；
- 命中的干扰项；
- 失败类型。

失败类型至少包括：

- `total_miss`：没有召回任何必要证据；
- `partial_evidence`：召回部分证据但不完整；
- `rank_too_low`：必要证据在较大 k 命中但小 k 未命中；
- `distractor_ahead`：错误干扰项排在 gold 前；
- `duplicate_crowding`：重复结果挤占 top-k；
- `version_conflict`：错误版本靠前；
- `filter_error`：规范或元数据过滤错误。

## 11. 数据集划分与防止过拟合

自动校验和专家抽检通过后，按 gold 证据而非按问题文本划分：

- `dev`：用于检索策略调试、权重调整和错误分析；
- `test`：冻结集，只用于阶段验收和回归；
- `challenge`：困难题、跨规范题、负例和历史失败案例。

同一证据或同一事实的不同语言改写必须位于同一集合，避免测试集泄漏到开发集。

每个数据集版本记录：

- 知识库规范版本；
- chunk schema 版本；
- 数据生成器版本；
- 提示词版本；
- embedding/检索配置；
- 专家审核批次；
- 创建日期。

---

## 12. 首版目标值

首版可将以下数值作为工程目标，而不是行业统一标准：

| 指标 | 初始目标 |
|---|---:|
| Group Recall@10 | ≥ 90% |
| Complete@10 | ≥ 80% |
| MRR | ≥ 0.70 |
| Distractor Hit@10 | ≤ 10% |
| 专家抽检错误率 | ≤ 5% |

任何核心查询类型的 `Complete@10` 不应比总体低超过 15 个百分点。

首次运行应先记录真实 baseline。若当前系统明显低于目标，优先用失败类型定位问题，不为达到单一总分而盲目调整。

---

## 13. 与现有实现的衔接

现有评测核心已经支持：

- 点查的 `hit@k` 和 `MRR`；
- 列举题的 `coverage@method_no`；
- `rag2 eval <dataset.json> [k]`；
- 使用 `chunk_id` 回查结构化元数据。

后续实现应增量扩展，而不是推翻现有能力：

1. 扩展数据集 schema，兼容当前 `gold_method_no`、`gold_clause_no` 和 `gold_methods`。
2. 将旧点查样本转换为只有一个 `must_have_group` 的样本。
3. 将旧覆盖查保留为领域聚合指标，或转换为多个 method 证据组。
4. 增加多证据、等价证据、可接受证据和干扰项指标。
5. 新增独立的数据集生成与校验工具，不把生成逻辑耦合进在线检索流程。
6. 评测运行仍直接复用真实 `text_retrieve`，保证离线指标与线上检索链一致。

---

## 14. 逻辑组件

生成与评测能力按职责拆为独立组件：

| 组件 | 输入 | 输出 | 职责 |
|---|---|---|---|
| Corpus Sampler | chunk cache、tree cache | 目标证据清单 | 按规范、章节和证据形态分层采样 |
| Evidence Pack Builder | 目标 chunk、结构树 | 有界证据包 | 补充父子、相邻、引用和跨条款证据 |
| Question Generator | 证据包、题型配额 | 结构化候选题 | 生成问题、证据组、参考答案和标签 |
| Variant Generator | 已通过初筛的问题 | 语言变体 | 生成口语、简称、长问题等有限变体 |
| Gold Validator | 问题、gold 证据 | 校验结论 | 检查可回答性、完整性、歧义和事实一致性 |
| Distractor Miner | 问题、全库 chunk 元数据 | 干扰项候选 | 发现相似方法、错误条件和版本冲突 |
| Dataset Curator | 全部候选及校验结果 | dev/test/challenge | 去重、配额平衡、证据级拆分和版本化 |
| Review Exporter | 待抽检样本 | 审核表 | 导出问题、证据、原文定位和审核字段 |
| Eval Runner | 冻结数据集、真实检索器 | 逐题结果 | 运行 top-20 一次并计算不同 k 的指标 |
| Report Writer | 逐题结果 | JSON/CSV/控制台报告 | 输出总览、分层指标和失败清单 |

生成工具与在线查询链保持隔离；评测运行器继续复用现有 C++ 检索实现。离线生成器采用何种语言不影响数据契约，实施计划应以批处理、结构化输出和可恢复性为优先选择。

## 15. 失败处理与可恢复性

- LLM 返回非法 JSON：记录原始响应，最多按固定次数重试；仍失败则标记 `generation_error`，不得静默修补关键 gold 字段。
- 引用了证据包外的 chunk：直接拒绝样本。
- `chunk_id` 失效：先通过 `stable_refs` 重新解析；无法唯一解析则标记 `stale_gold`，不参与评分。
- 同一稳定条款解析到多个 chunk：只有在这些 chunk 经确认语义等价时才放入同一 group，否则进入人工复核。
- API 中断或限流：每个阶段写 checkpoint，可从未完成样本继续，不重复生成已完成批次。
- 自动校验意见冲突：标记 `needs_review`，不得自动进入冻结测试集。
- 某一题型自动淘汰率异常高：停止该类别继续扩量，先检查采样规则、证据包或提示词。
- 评测期间 PG、Milvus 或 embedding 服务失败：整次运行标记为无效，不将部分样本统计为 miss。

所有失败保留机器可读的 `error_code` 和简短原因，便于统计系统性问题。

## 16. 测试策略

### 16.1 纯函数单元测试

- 必要证据组命中、漏失和等价 chunk 命中；
- `Group Recall@k` 与 `Complete@k`；
- MRR 边界和 miss；
- nDCG 中同组重复证据不重复增益；
- 无干扰项样本不进入 `Distractor@k` 分母；
- `Redundancy@k` 的同组、同方法和重复文本判定；
- 旧 `EvalCase` 到新 schema 的兼容解析；
- 按证据分组的确定性 dev/test/challenge 划分；
- 失效 `chunk_id` 的稳定引用回解析。

### 16.2 生成管道契约测试

使用固定的小型 chunk/tree fixture 和模拟 LLM 响应验证：

- 合法候选进入下一阶段；
- 非法 JSON、越界事实和缺失证据被拒绝；
- 语言改写不会修改 gold；
- 同一事实的近重复样本被合并；
- checkpoint 重跑不会产生重复 `case_id`。

### 16.3 集成验收

- 对小型固定数据集运行真实 `text_retrieve`；
- 一次取得 top-20，再正确派生各个 k 的指标；
- JSON、CSV 和控制台汇总数字一致；
- 单条失败可回溯到规范、条款和 chunk 原文；
- 外部服务故障时不生成误导性的部分评测报告。

---

## 17. 不做

- 不评价最终回答的事实正确性、引用正确性或语言质量。
- 不让当前检索器参与 gold 的产生。
- 不将 LLM 自动评分直接视为领域专家金标。
- 不在首版实现通用跨行业数据集。
- 不用单一 Recall 或单一总分代表全部召回质量。
- 不在 RRF 分数未经校准时直接制定跨问题统一拒答阈值。
- 不因当前知识库规模较小而生成数千条低质量、近重复问题。

---

## 18. 验收标准

1. 能从少于 10 份规范中分层生成约 400 条候选题。
2. 自动校验后保留约 250～300 条结构合法、证据可追踪的样本。
3. 支持 §5 的八类查询、三级难度和不可回答负例。
4. 每个正例样本至少有一个必要证据组，并同时保存 `chunk_id` 与稳定条款定位。
5. 专家可按统一审核表抽检 50～100 条。
6. 抽检错误率满足 §8.3 的冻结门槛。
7. 评测命令可输出 §9 的核心指标以及 §10 的分层报告和失败清单。
8. 数据集按 gold 证据划分 dev/test/challenge，语言改写不得跨集合泄漏。
9. §16 的纯函数、生成管道和集成测试通过。
10. 测试集冻结后，任何检索逻辑调整都能用同一版本数据集重复运行和比较。
