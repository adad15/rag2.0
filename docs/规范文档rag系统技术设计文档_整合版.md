## 0. 文档定位

> 面向工程技术规范、道路桥梁规范、试验规程、材料标准等专业文档，构建一个以 C++ 为主程序、Python/GPU 服务为模型推理层、PostgreSQL 为结构化底座、Milvus 为向量与稀疏索引的规范文档 RAG 系统。

系统目标不是做通用问答，而是做“可溯源、可维护、可评估、可持续更新”的规范知识检索与辅助决策系统。
## 1. 设计目标

### 1.1 核心目标

本系统需要解决以下问题：
1. 将 PDF、扫描版 PDF、DOCX 等规范文件解析为结构化知识库；
2. 保留规范的标准号、条款号、章节层级、表格、公式、强制性条文、版本状态等关键信息；
3. 支持用户通过自然语言检索规范条文；
4. 支持按标准号、条款号进行精确查询；
5. 支持表格、限值、单位、工程参数类问题的可靠检索；
6. 支持扫描件、图纸、示意图、复杂表格等视觉密集内容的补充召回；
7. 生成回答时必须给出标准号、规范名称、版本、条款号等来源信息；
8. 对召回不足、版本冲突、废止规范等情况必须进行明确提示或拒答；
9. 支持后续规范更新、废止、替代、重建索引和模型升级。
### 1.2 非目标

第一阶段不追求：
1. 所有模型全部本地 C++ 推理；
2. 视觉路和文本路同时全量上线；
3. 对所有图纸进行深度理解；
4. 完全自动替代人工规范审查；
5. 没有评估集时盲目追求复杂融合。

系统首先应成为一个稳定的“规范条文检索 + 溯源回答”平台，然后逐步扩展为多模态规范理解系统。
## 2. 总体设计原则

### 2.1 C++ 负责确定性编排，模型推理服务化

系统整体采用“C++ 主程序 + Python/GPU 服务”的混合架构。

C++ 主程序承担：
- 文件入库流程编排；
- 调用解析服务；
- 条款层级树构建；
- 规则分片；
- 元数据抽取与校验；
- PostgreSQL 写入；
- Milvus 写入；
- 查询路由；
- 多路召回；
- RRF 融合；
- small-to-big 上下文回填；
- 生成端 Prompt 组装；
- 版本维护与索引更新调度。

Python/GPU 服务承担：
- MinerU 文档解析；
- OCR、版面分析、公式识别、表格还原；
- 文本 Embedding；
- 视觉 Embedding；
- 文本 Reranker；
- 视觉 Reranker。

设计原则是：
> 确定性逻辑放在 C++；重模型推理和文档视觉理解放在 Python/GPU 服务。

### 2.2 文本路为主，视觉路为补充

规范问答的主要依据仍然是条款文本。因此第一主线是文本路：
```text
规范文件 → 解析 → 条级分片 → 文本向量 + BM25 + 精确匹配 → 条款召回 → 溯源生成
```

视觉路用于补充以下场景：
- 扫描件 OCR 质量差；
- 图纸、示意图、流程图较多；
- 表格结构复杂；
- 页面版式对理解问题有重要影响；
- 用户明确询问图、表、页面布局或扫描内容。

视觉路不应替代文本路，而应作为补充召回能力。

图片、示意图、图表类内容在文本路中的第一优先级不是直接做视觉检索，而是作为条款的附加证据：先利用图题、所在页、相邻条款和 block 位置建立关联；图题 caption 可进入对应条款的 `retrieval_text`，图片本体则作为附件回显或后续视觉路索引对象。

### 2.3 PostgreSQL 是系统底座

无论走文本路还是视觉路，最终都必须回到 PostgreSQL 中的结构化底座。

PostgreSQL 保存：
- 标准基本信息；
- 版本状态；
- 替代关系；
- 章节层级树；
- 条款原文；
- 表格结构化结果；
- 公式；
- 图表信息；
- 页码到条款映射；
- block 到条款映射；
- 强制性条文标记；
- 条文说明标记；
- 引用关系。

Milvus 只负责召回，不作为唯一知识源。

### 2.4 条款号原子性不能破坏

规范条款具有工程引用和法律引用意义。

因此数据库中必须保留条款原子性：
```text
一个 clause_id 对应一个规范条款或一个明确的款/项单元。
```

可以为检索构造扩展文本，但不能把多个条款不可逆地合并为一个失去边界的知识单元。

## 6. 文档解析流程

### 6.1 输入类型

系统支持：
1. 原生 PDF；
2. 扫描版 PDF；
3. DOCX；
4. 图片文件；
5. 后续可扩展 PPTX、XLSX。

### 6.2 解析主流程
```text
文件导入
  ↓
文件类型判断
  ↓
调用 MinerU 解析服务
  ↓
获得结构化 JSON / Markdown / HTML / 图像块信息
  ↓
C++ 统一归一化
  ↓
生成标准信息、层级树、条款、表格、公式、页码映射
  ↓
解析质量检查
  ↓
写入 PostgreSQL
```

### 6.3 MinerU 解析内容

MinerU 需要输出或经后处理补齐以下内容：
- 文档标题；
- 标准号；
- 目录层级；
- 章、节、条、款、项；
- 正文文本；
- 表格 HTML；
- 公式 LaTeX；
- 图题；
- 表题；
- 页码；
- OCR 置信度；
- 页面 block；
- block 坐标；
- 阅读顺序。
### 6.4 DOCX 处理

DOCX 默认可交给 MinerU 统一处理。

但如果需要更高精度识别：

- 标题样式；
- 黑体强制性条文；
- 表格结构；
- 页眉页脚；

则可使用 python-docx 进行增强解析。
### 6.5 Tesseract 的定位

Tesseract 不作为主路线重复 OCR。

推荐定位：
1. 无 GPU 环境下的轻量 OCR 备选；
2. 对少量低质量页面做补充识别；
3. 对 MinerU 解析失败页面进行兜底。

主线仍以 MinerU 为准。

### 6.6 poppler 的定位

poppler 在系统中仍然重要：
1. 读取 PDF 元信息；
2. 对原生 PDF 做快速文本抽取；
3. 将页面渲染为图像，供视觉路使用；
4. 为 OCR 或人工质检生成页面图片；
5. 生成 page image 和 block image 的基础素材。
## 7. 分片设计

### 7.1 基本原则

规范分片不应采用普通字符滑窗作为主方法。

主分片单位应是：
```text
章 → 节 → 条 → 款 → 项
```

其中条是默认检索基本单元。

### 7.2 原子条款与检索文本分离

为避免破坏条款号，应采用：

```text
atomic_text：原子条款文本
retrieval_text：用于检索的扩展文本
context_text：用于生成的父级上下文
```

示例：
```text
atomic_text = 4.2.1 条款自身内容
retrieval_text = 标准号 + 标准名称 + 章节路径 + 4.2.1 条文 + 关键词 + 单位
context_text = 4.2 所属节的完整内容
```

这样既保证条款号精确，又提升语义检索质量。

若条款附近存在表题、图题或图表题，`retrieval_text` 应纳入这些 caption；caption 不应单独成为主检索条款，而应增强其所属条款的可召回性。

### 7.3 短条款处理

短条款不建议在数据库层面直接合并。

可采用：
1. 原子条款单独保存；
2. 检索文本中加入相邻条款标题或父级节标题；
3. 召回后通过 small-to-big 回填父级节；
4. 生成时仍按原始条款号引用。

### 7.4 长条款处理

长条款可按款、项、列项拆分，但必须保留父条款号。

例如：
```text
4.3.2
4.3.2-1
4.3.2-2
4.3.2-a
```

拆分后仍应能回溯到完整的 4.3.2。
### 7.5 表格与公式处理

表格和公式不应与其所属条款割裂。

处理原则：
1. 表格有独立 ID；
2. 表格归属到对应条款；
3. 表格 caption 进入检索文本；
4. 表格 HTML 和结构化 cell 均保存；
5. 公式 LaTeX 保存并与条款绑定；
6. 公式不得被字符切片拆散。

### 7.6 图片与图题处理

图片不作为文本路的主检索单元。解析阶段识别到 `figure_title`、`chart_title` 或以“图/附图”开头的 caption 时，应将其挂到最近的所属条款：

1. 图题 caption 进入该条款的 `retrieval_text`；
2. 条款节点记录 `attached_figures` 或等价附件关系；
3. 仅保存 caption、页码、bbox 等轻量定位信息；
4. 图片裁剪、`image_path`、视觉向量检索后置到视觉路 M7/M8。

这样用户问到“示意图/构造图/流程图”时，文本路可先命中相关条款；图片本体作为证据附件回显，必要时再由视觉路补充召回。
## 8. 入库流程

### 8.1 公共入库流程

```text
1. 文件进入待入库队列
2. C++ 记录文件信息与任务 ID
3. 调用 MinerU 解析服务
4. 获得统一中间格式
5. C++ 构建层级树
6. 抽取标准号、版本、页码、条款号、表格、公式、图题
7. 生成 page_clause_map 与 page_blocks
8. 解析质量检查
9. 写入 PostgreSQL
10. 生成 retrieval_chunks
11. 调用文本 Embedding 服务
12. 写入 Milvus clause_text collection
13. 必要时渲染页面图像
14. 调用视觉 Embedding 服务
15. 写入 Milvus page_visual 或 block_visual collection
16. 更新入库状态
```

### 8.2 文本路入库

文本路是第一阶段主线。

流程：
```text
PostgreSQL 条款节点
  ↓
生成 retrieval_text
  ↓
调用文本 Embedding 服务
  ↓
写入 Milvus clause_text
  ↓
建立 dense 索引 + BM25 索引 + 标量过滤字段
```

Milvus `clause_text` 建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunk_id` | string | chunk ID |
| `standard_id` | string | 标准 ID |
| `standard_no` | string | 标准号 |
| `standard_name` | string | 标准名称 |
| `clause_no` | string | 条款号 |
| `status` | string | 现行 / 作废 / 即将实施 |
| `access_level` | string | 权限/密级，作为标量过滤字段（见 §9.6） |
| `is_mandatory` | bool | 是否强制性条文 |
| `path` | string | 章节路径 |
| `text` | varchar | 用于保存原文本（配合 Milvus 2.5 TEXT 索引或供回查） |
| `sparse` | SparseFloatVector | 用于 BM25 的稀疏向量（Milvus 2.4+） |
| `dense` | float_vector | 文本向量 |

注意：若使用 Milvus 内置全文检索，必须配置专门的中文 analyzer（如 JIEBA）；若使用稀疏向量，则可在外部利用 BGE-M3 等模型生成稀疏向量写入 `sparse` 字段。
### 8.3 视觉路入库

视觉路作为第二阶段或第三阶段增强能力。

初始版本可采用 page 级索引：
```text
PDF 页面渲染
  ↓
页面图像
  ↓
调用 Qwen3-VL-Embedding
  ↓
写入 Milvus page_visual
```

更推荐预留 block 级能力：
```text
页面图像
  ↓
版面 block 裁剪
  ↓
block 图像向量化
  ↓
写入 Milvus block_visual
  ↓
block → clause 映射
```

Milvus `page_visual` 建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `page_id` | string | 页面 ID |
| `standard_id` | string | 标准 ID |
| `standard_no` | string | 标准号 |
| `page_no` | int | 页码 |
| `status` | string | 版本状态 |
| `image_path` | string | 页面图像路径 |
| `visual` | float_vector | 视觉向量 |

Milvus `block_visual` 建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `block_id` | string | block ID |
| `standard_id` | string | 标准 ID |
| `page_no` | int | 页码 |
| `block_type` | string | text/table/figure/formula |
| `related_node_id` | string | 关联条款 |

| `image_path` | string | 裁剪图路径 |
| `visual` | float_vector | 视觉向量 |
## 9. 检索模式设计

### 9.0 查询理解与预处理（前置流程）

所有检索模式（text / visual / both / auto）执行前，必须先经过统一的查询理解层。该层由 C++ 主程序承担确定性部分，是 MVP 阶段决定召回上限与路由准确率的关键，不可省略。

#### 9.0.1 标准号 / 条款号解析与归一化

用户问题中的标准号写法高度不统一，且分词器会切碎带斜杠、连字符的 token，因此**不能依赖 BM25/dense 召回标准号**，必须前置做规则解析与归一化。

需要处理的等价写法示例：

```text
JTG D60-2015 / JTG/T D60 / JTGD60 / D60 规范 / 《公路桥涵设计通用规范》
```

解析器要求：
1. 维护标准号正则族（国标 GB/GB/T、行标 JTG/JTJ/TB、地标、团标 T/CECS 等各自格式）；
2. 抽取后归一化为内部 `standard_no`（去空格、统一斜杠与连字符、年份可缺省匹配）；
3. 维护"标准名称 ↔ standard_no"别名表，支持用书名号内全称/简称命中；
4. 年份容错：用户不带年份时，默认指向 `status=现行` 的版本；
5. 条款号解析支持 `4.2.1`、`4.2.1-1`、`4.2.1-a`、"第 4.2.1 条"等写法，归一化到 `clause_no`。

解析结果作为结构化过滤条件直接进入 PG 精确匹配与 Milvus 标量过滤，而非进入向量召回。

#### 9.0.2 领域同义词 / 别名词典

材料名、试验名、指标名在规范中别名极多（如"沥青混合料"↔"AC"、"压实度"↔"密实度"）。纯 dense + BM25 易召不全。

要求：
1. 建立领域同义词词典（材料、试验、工艺、指标、缩写）；
2. 用于查询扩展：在 BM25 路对查询做同义词扩展；
3. 词典与 §12.3 轻量语义元数据抽取共用同一份术语库，保证入库与查询两侧口径一致。

#### 9.0.3 中文分词自定义词典

§8.2 配置的中文 analyzer（如 JIEBA）必须加载自定义词典，否则专业术语与标准号在 BM25 上会被切碎导致召回塌陷。

自定义词典至少包含：
1. 规范术语与缩写；
2. 标准号格式 token（如 `JTG/T`、`GB/T`）作为整体保护；
3. 材料/试验/指标专名。

自定义词典、同义词词典应纳入版本管理，更新后需触发受影响文档的 BM25 重建并记录词典版本。

### 9.1 查询模式

系统支持四种模式：
```text
auto
text
visual
both
```

推荐默认使用 `auto`。
### 9.2 text 模式

text 模式是主模式。

流程：
```text
用户问题
  ↓
查询预处理 / 可选查询改写
  ↓
文本 Embedding
  ↓
Milvus dense 召回
  ↓
Milvus BM25 召回
  ↓
PostgreSQL 标准号/条款号精确匹配
  ↓
RRF 融合
  ↓
文本 Reranker
  ↓
small-to-big 回填
  ↓
构造上下文
  ↓
DeepSeek 生成回答
```

text 模式三路召回：

| 召回方式 | 作用 |
|---|---|
| dense 召回 | 语义相似问题 |
| BM25 召回 | 关键词、术语、材料名称、指标名称 |
| PG 精确匹配 | 标准号、条款号、明确编号 |
### 9.3 visual 模式

visual 模式用于图、表、扫描页等视觉内容。

流程：
```text
用户问题
  ↓
视觉 Embedding 编码 query
  ↓
Milvus page_visual / block_visual 召回
  ↓
视觉 Reranker
  ↓
page/block → clause 映射
  ↓
回查 PostgreSQL 条款文本与表格
  ↓
构造上下文
  ↓
DeepSeek 生成回答
```

注意：视觉路检索的是页面或 block，但生成时仍应回到条款文本和结构化表格。
### 9.4 both 模式

both 模式同时运行文本路和视觉路。

流程：
```text
text 候选条款
       \
        → clause_id 归一化 → 去重 → 融合 → 重排 → 生成
       /
visual 命中页面/block → 映射条款
```

both 模式最全，但成本最高。

不建议作为默认模式。
### 9.5 auto 模式

auto 模式由 C++ 查询路由模块判断使用哪条路线。

建议规则：

| 查询特征 | 推荐路线 |
|---|---|
| 含标准号 | text |
| 含条款号 | text |
| 含“表”“限值”“指标”“单位” | text + table |
| 含“图”“示意图”“流程图”“第几页” | visual 或 both |
| 命中文档 OCR 质量低 | visual |
| text 召回置信度低 | fallback visual |
| visual 映射条款不清 | fallback text |

### 9.6 统一过滤：状态 + 密级

无论何种检索模式，以下两类过滤必须强制作用于**每一次**召回，作为不可绕过的基线条件，优先级高于相关性排序：

1. **版本状态过滤**：默认 `status = 现行`，仅当用户显式查询历史/废止版本时放开（见 §13.1）；
2. **密级 / 权限过滤**：依据请求方的 `access_level` 过滤可见标准（对应 §5.1 `access_level` 字段）。

实现要求：
1. 上述两个条件同时作为 **Milvus 标量过滤字段**和 **PostgreSQL 查询条件**下推，不能只在召回后用应用层兜底；
2. `status` 与 `access_level` 必须随入库写入 Milvus 标量字段（§8.2 `clause_text` schema 需补 `access_level` 字段）；
3. 与 §13.4 一致性机制配合：Milvus 标量可能滞后，最终以 PG 回查为准，但密级过滤**禁止**依赖可能滞后的 Milvus 字段单独裁决——召回后必须用 PG 最新 `access_level` 二次校验，任一不通过即剔除。

> 密级过滤属于安全底线，任何检索路径（含 visual、both、fallback）都不得绕过。

### 9.7 表格限值问答子流程

测试集中表格 / 限值 / 数值类问题占比很高（见 §15.2），仅靠"召回表 caption + small-to-big 回填"无法稳定回答"某材料某等级的限值是多少"这类需要**精确行列定位**的问题。因此在命中表格后增加结构化定位子流程：

```text
查询理解（抽取材料/等级/指标/单位条件）
  ↓
dense + BM25 召回 table caption / table_summary  → 命中 table_id
  ↓
在 spec_table_cells 上做结构化过滤
  （按 row_header / col_header / unit 匹配查询条件）
  ↓
定位目标单元格 number_value + unit + merged_info
  ↓
连同 table_caption、所属 clause_no 一起注入上下文
  ↓
DeepSeek 生成（引用表号 + 行列条件 + 条款号）
```

要点：
1. 表格召回命中的是表，但回答依据是**单元格**，必须把命中的 `number_value` / `unit` 显式带入上下文，供 §11.4 数值后置校验做硬匹配；
2. 结构化过滤匹配不到唯一单元格时，回退为注入紧凑 Markdown 表格片段（见 §11.3 表格片段化），由模型在受控片段内作答，而非塞入完整 HTML；
3. 合并单元格依据 `merged_info` 还原表头归属，避免行列错位导致取错限值。
## 10. 融合与重排

### 10.1 RRF 融合与分数归一化

text 模式中 dense、BM25、PG 精确匹配三路召回后，默认可使用 RRF 进行粗排融合。

RRF 的优点：
1. 不需要人工复杂调权重；
2. 对不同检索器分数尺度不敏感；
3. 对专业规范这种多查询类型场景更稳健。

**注意**：在 `both` 模式下跨模态融合时，由于文本向量与视觉向量底层模型不同，分数分布差异极大，仅依赖 RRF 可能会导致某一路（如视觉线索）被严重稀释。建议在此场景下增加**分数归一化（Score Normalization）**步骤，或者在多路并发召回后，统一交由多模态 Reranker（如 Qwen3-VL-Reranker）进行统一打分，避免硬性 RRF 带来的偏差。

### 10.2 去重策略

所有候选最终应归一到：

```text
standard_id + node_id / clause_id
```

去重优先级：
1. 完全相同 clause_id 合并；
2. 同一条款不同 chunk 合并；
3. 同一父条款下多个子项保留但标记关联；
4. 文本路与视觉路命中同一条款时合并证据。

### 10.3 Reranker

第一阶段可以先不启用 Reranker，建立 baseline。

第二阶段加入文本 Reranker。

视觉路启用后，再加入视觉 Reranker。

推荐策略：

| 阶段 | 策略 |
|---|---|
| MVP | 无 reranker，仅 RRF |
| 文本增强 | 文本 reranker top 20 → top 5 |
| 视觉增强 | 视觉 reranker page/block top 20 → top 5 |
| 成本优化 | 低置信度或复杂问题才触发 reranker |
### 10.4 small-to-big 回填

召回以条款为小单元，生成时需要父级上下文。

回填策略：
1. 命中条款；
2. 查询父级节；
3. 附带相邻条款；
4. 附带相关表格和公式；
5. 控制上下文长度；
6. 仍以命中条款作为主要引用对象。

### 10.5 引用图扩展回填

规范条款大量出现"应符合 4.3.2 的规定""按本规范第 6 章执行""引用 GB xxxx"等交叉引用。命中条款若只回填父级节，常缺失被引用条款，导致回答不完整。利用已有的 `clause_nodes.refs`（条款/标准引用）与 `standards.replaces / replaced_by` 字段，在 small-to-big 之外增加一跳引用图扩展：

回填策略：
1. 命中条款后，解析其 `refs`，沿引用边做**一跳**扩展，拉取被引用条款 / 表格作为补充证据；
2. 跨标准引用时，被引用标准同样要过 §9.6 的 `status` 与 `access_level` 过滤；
3. 扩展深度默认 1 跳，受上下文预算约束（见 §11.5 token 预算），避免引用链爆炸；
4. 扩展进来的条款作为**辅助证据**标注，引用归属仍以原命中条款为主对象；
5. 若被引用标准已废止而原条款现行，按 §13 提示版本风险，不静默采用。

> 引用图扩展是规范 RAG 区别于通用 RAG 的结构化优势，建议在第二阶段（文本路增强）与 reranker 一并上线，并用评估集验证其对"条款命中率/答案完整性"的增益、对噪声的影响（呼应 §15.1 small-to-big 是否引入噪声的评估项）。
## 11. 生成设计

### 11.1 生成模型

最终回答由 DeepSeek API 完成。

C++ 主程序负责：
1. 构造上下文；
2. 注入标准号、条款号、状态、强制性标记；
3. 编写系统约束；
4. 调用 DeepSeek；
5. 解析返回；
6. 做溯源校验。

### 11.2 强制约束

生成端必须遵守：
1. 只能依据检索上下文回答；
2. 必须标明标准号、标准名称、版本、条款号；
3. 涉及强制性条文必须明确提示；
4. 涉及废止或非现行标准必须提示；
5. 多版本冲突时优先现行标准；
6. 未检索到依据时必须拒答；
7. 不允许编造条款号、限值、单位；
8. 表格问题应引用表号、行列条件或相关条款。

### 11.3 生成上下文格式

建议上下文采用结构化片段：

```json
{
  "source_id": "S1",
  "standard_no": "JTG xxxx-xxxx",
  "standard_name": "xxxx规范",
  "status": "现行",
  "clause_no": "4.2.1",
  "path": "第4章 / 4.2 xxxx / 4.2.1",
  "is_mandatory": true,
  "text": "条款原文……",
  "tables": [],
  "formulas": []
}
```

*说明*：工程规范中的表格往往非常巨大，直接将完整 HTML 表格放入 `tables` 数组极易导致大模型 Context 溢出或注意力涣散。在组装上下文前，建议加入**表格片段化（Table Chunking）**策略——仅提取与 Query 高度相关的行列，或将其转换为紧凑的 Markdown 表格格式注入。

回答中引用：
```text
依据《xxxx规范》（JTG xxxx-xxxx）第 4.2.1 条……
```

### 11.4 拒答与后置校验策略

以下情况应拒答或提示不足：
1. top 候选分数过低；
2. 候选条款不包含关键术语；
3. 多个候选互相冲突且无法判断版本；
4. 只召回到条文说明，未召回正文条文；
5. 问题要求的标准不在库中；
6. 问题属于规范外的经验判断，无法从规范直接支持。

**大模型数值幻觉拦截（Post-verification）**：
除 Prompt 约束外，系统层应增加生成后置校验模块。在 DeepSeek 返回结果后，利用正则提取回答中的数值、限值和单位，并与召回的 PostgreSQL 原文进行硬匹配。若发现数值篡改或单位不一致，系统应强行拦截并提示用户”未能准确生成数值，请直接参考给出的规范原文”。

**拒答阈值的标定**：
上面”top 候选分数过低”等阈值不能拍脑袋设定，必须在 §15 评估集上校准：
1. 每一路检索器（dense / BM25 / reranker）分数尺度不同，需各自标定阈值，或统一以 reranker 分数为准；
2. 用评估集中的”应拒答”样本（标准不在库、规范外经验判断）与”应作答”样本，绘制阈值-召回/误拒曲线，选取满足”废止标准误用率、无依据拒答准确率”目标的工作点；
3. 阈值随模型/索引版本变化需重新标定，纳入 §14.3 索引版本记录。

### 11.5 上下文 token 预算

small-to-big 回填（§10.4）、引用图扩展（§10.5）、表格片段（§11.3）都会向上下文追加内容，需要统一的预算分配，避免 Context 溢出或注意力涣散：
1. 为单次生成设定总 token 预算，并按优先级分配：命中条款原文 > 表格相关行列 > 父级节上下文 > 一跳引用条款；
2. 超预算时按上述优先级自低向高裁剪，命中条款原文不可裁剪；
3. 表格一律走片段化注入（§11.3 / §9.7），禁止注入完整大表 HTML；
4. 预算与命中条款数量自适应：候选越多，每条分配的上下文越短。
## 12. 元数据生成策略

### 12.1 元数据分层

不要把所有元数据都依赖 LLM 生成。

建议分为三层：

| 层级 | 方法 | 是否必须 |
|---|---|---|
| 规则元数据 | 正则、层级树、条款号、页码、文件名 | 必须 |
| 轻量语义元数据 | 关键词、数字、单位、引用标准 | 必须 |
| LLM 增强元数据 | 摘要、适用条件、实体关系 | 可选 |

### 12.2 规则元数据

包括：
- 标准号；
- 标准名称；
- 版本年份；
- 条款号；
- 章节路径；
- 页码；
- 条文说明；
- 表号；
- 图号；
- 公式编号；
- 强制性标记。

### 12.3 轻量语义元数据

通过规则或本地 NLP 抽取：
- 数值；
- 单位；
- 材料名称；
- 试验名称；
- 工程对象；
- 引用标准；
- 指标名称。

### 12.4 LLM 增强元数据

DeepSeek 可用于离线增强：
- 条款摘要；
- 适用条件；
- 关键词；
- 实体关系；
- 常见问法。

建议作为后台任务，不阻塞主入库流程。
## 13. 版本管理与维护

### 13.1 版本状态是高优先级能力

规范 RAG 的核心风险之一是误用废止标准。

系统默认只召回：
```text
status = 现行
```

除非用户明确查询历史版本。
### 13.2 版本字段

必须维护：
- 发布日期；
- 实施日期；
- 废止日期；
- 替代标准；
- 被替代标准；
- 局部修订；
- 状态来源；
- 状态核验时间。
### 13.3 更新流程

#### 新增标准
```text
新文件 → 解析 → 质检 → 入 PG → 建索引 → 标记现行/即将实施
```
#### 改版标准
```text
新版入库 → 旧版 status 改为作废 → 建立 replaces/replaced_by → 重建相关索引
```
#### 废止标准
```text
PG 状态改为作废 → Milvus 标量字段同步更新 → 默认召回过滤
```
#### 局部修订 / 修改单（条款级版本）

国标、行标常发布"修改单"：标准整体仍现行，仅个别条款被替换或新增。这类变更不能套用"整本改版"流程，需做条款级版本管理：
```text
修改单入库 → 定位受影响 clause_id
  → 旧条款节点 status 置为 作废/被修订，记录修订来源与生效日期
  → 写入新条款节点，建立 supersedes 指向旧条款
  → 仅对受影响条款重建 retrieval_chunks 与向量索引
  → 标准整体 status 保持 现行
```
要点：
1. 条款节点（§5.2 `clause_nodes`）需支持条款级 `status` 与修订指向，默认只召回最新现行条款；
2. 受影响范围最小化：只重建被修订条款的索引，不整本重建；
3. 用户查历史条款时可显式放开，回答需提示"该条款已被 X 年修改单替换"。
### 13.4 原子化维护

一份文档的以下内容应作为一个维护单元：
1. PostgreSQL 标准记录；
2. PostgreSQL 条款树；
3. 表格结构化数据；
4. 文本向量索引；
5. 视觉向量索引；
6. 文件与页面图像。

避免出现 PG 已更新、Milvus 未更新，或文本路已更新、视觉路未更新的问题。

**一致性保障机制**：
在分布式环境中，向量库更新存在延迟或失败的可能。建议采取以下对策：
1. **异步对齐/补偿**：后台开启对齐任务，定期校验 PG 与 Milvus 的数据一致性状态。
2. **查询时以 PG 状态为准**：检索流程中，当 Milvus 召回候选片段后，必须在 C++ 路由层通过 `clause_id` 回查 PG 的最新 `status`。若 PG 中该条款或标准已标记为作废/删除，即使 Milvus 尚未清理，也必须将其过滤出局。

## 15. 评估体系

### 15.1 为什么评估要前置

没有评估集，无法判断：

1. 文本路是否有效；
2. BM25 中文分词是否有效；
3. Reranker 是否提升；
4. Qwen3-Embedding 是否优于轻量模型；
5. 视觉路是否值得；
6. both 模式是否真的提升；
7. small-to-big 是否引入噪声。

### 15.2 测试集设计

建议第一阶段建立 100 条左右测试集。

| 类型 | 数量 |
|---|---:|
| 标准号/条款号精确查询 | 20 |
| 普通语义查询 | 20 |
| 限值/数值/单位查询 | 20 |
| 表格查询 | 15 |
| 强制性条文查询 | 10 |
| 废止/现行版本查询 | 10 |
| 图纸/扫描页/视觉问题 | 5-10 |

每条测试数据包括：

```json
{
  "question": "问题",
  "gold_standard_no": "应命中的标准号",
  "gold_clause_no": "应命中的条款号",
  "gold_answer": "参考答案要点",
  "gold_page": "页码",
  "gold_table_id": "表格 ID",
  "must_cite": true
}
```

### 15.3 检索指标

- recall@k；
- MRR；
- top-1 条款命中率；
- top-3 条款命中率；
- 标准号命中率；
- 表格命中率；
- 视觉页命中率；
- 页命中后条款映射成功率。

### 15.4 生成指标

- 答案正确性；
- 条款号引用准确率；
- 标准版本准确率；
- 强制性条文标注准确率；
- 废止标准误用率；
- 无依据拒答准确率；
- 数值和单位准确率。

### 15.5 评估集的标注流程与在线增长

100 条起步集需要明确的来源与持续扩充机制，否则评估闭环（§15.1）无法长期成立：
1. **标注来源**：由熟悉规范的人员从真实使用场景出题，金标（标准号 / 条款号 / 表格 ID / 参考答案要点）人工标注并复核；
2. **难例覆盖**：刻意纳入"应拒答"样本（标准不在库、规范外经验判断、废止标准诱导），用于标定 §11.4 拒答阈值；
3. **在线回流**：上线后采集用户查询、命中条款、是否采纳/纠错等信号，定期挑选高频与失败 case 经人工确认后回流扩充评估集；
4. **回归保护**：每次模型/索引/词典升级前后跑同一评估集做回归对比（呼应 §17.2 回归评估），防止指标隐性退化。
## 16. 部署方案

### 16.1 单机开发部署

适用于第一阶段开发。

组件：
- Windows + VS2022 + vcpkg；
- C++ 主程序；
- PostgreSQL；
- Milvus；
- Python venv / conda；
- MinerU 服务；
- DeepSeek API；
- 可选本地轻量 embedding 服务。

第一阶段可不强制部署视觉 embedding。

### 16.2 GPU 服务部署

适用于第二阶段和第三阶段。

建议将以下服务独立部署：
- MinerU 服务；
- Qwen3-Embedding 服务；
- Qwen3-Reranker 服务；
- Qwen3-VL-Embedding 服务；
- Qwen3-VL-Reranker 服务。

### 16.3 显存与成本控制

不要让多个 8B 模型无脑常驻。

建议：
1. 文本 embedding 优先常驻；
2. reranker 可按需触发；
3. 视觉 embedding 低频时按需加载；
4. 视觉 reranker 可先不用；
5. embedding 维度可截短到 1024 或 2048；
6. 视觉路只对必要文档建索引。

### 16.4 服务韧性与延迟预算

一次查询会串联 Embedding、Milvus（×2）、Reranker、PG、DeepSeek 等多个独立服务，任一不可用都会影响可用性，需明确降级与延迟策略：

1. **超时与重试**：每个外部服务设独立超时与有限重试；DeepSeek 等生成调用失败时优先返回"检索到的规范原文 + 无法生成"的降级回答，而非整体报错。
2. **分级降级链**：
   - Reranker 不可用 → 退回仅 RRF 排序（对应 §10.3 MVP 策略）；
   - 视觉服务不可用 → both/visual 自动退回 text；
   - Embedding 不可用 → 退回 BM25 + PG 精确匹配，并提示语义召回降级。
3. **延迟预算**：为查询链路设定 P95 目标，按阶段拆分预算（embedding / 召回 / rerank / 生成），超预算阶段触发降级。
4. **缓存层**：对高频查询的 query embedding 与最终上下文做缓存；标准号/条款号精确查询结果可短期缓存。缓存键需包含 `access_level` 与索引版本，避免越权命中或读到旧索引。

### 16.5 Embedding 模型升级与索引迁移

更换文本/视觉 embedding 模型会使旧向量失效，必须全量重建，需要灰度迁移而非停机重建：
1. 新模型以新 collection（或带 `index_version` 区分）并行建索引，旧索引继续对外服务；
2. 在评估集上对比新旧索引指标（§15），达标后再切流；
3. 切换以 `index_version` 灰度放量，保留回滚能力；
4. 迁移期间写入需双写或排队，迁移完成后清理旧索引；
5. `embedding 维度`、模型版本、`index_version` 记入 §14.3 追溯信息。

## 18. 风险与修改建议

### 18.1 主要风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 架构过重 | 第一版同时上双路会难以调试 | 文本路优先 |
| OCR 错误 | 表格数字、单位错会导致严重误答 | 入库质检 + 人工复核 |
| 条款号错位 | 生成引用错误条款 | 条款号规则校验 |
| 表格不可控 | HTML 表格难以稳定回答限值问题 | 单元格结构化 |
| 视觉页级过粗 | 命中页面但无法准确定位条款 | 预留 block 级映射 |
| 版本误用 | 回答废止标准 | status 过滤 + 状态来源 |
| DeepSeek 成本高 | 每 chunk 调用会慢且贵 | LLM 元数据离线化 |
| GPU 成本高 | 多个 8B 常驻压力大 | 按需加载 + 小模型变体 |
| both 模式不一定提升 | 可能只是更贵 | 必须用评估集验证 |
| 标准号召不准 | 写法不一、分词切碎导致精确匹配失效 | 前置标准号解析归一化（§9.0） |
| 密级越权 | 检索未按权限过滤导致泄露 | status+密级统一下推过滤（§9.6） |
| 服务级联失败 | 多服务串联任一挂掉即不可用 | 分级降级 + 延迟预算（§16.4） |
| 修改单漏更新 | 标准现行但个别条款已修订仍被召回 | 条款级版本管理（§13.3 局部修订） |

### 18.2 必须修改点

1. 第一版不要全量实现双路召回；
2. 查询模式增加 `auto`；
3. 视觉路预留 block 级结构；
4. 表格必须结构化建表；
5. 条款原子性必须保留；
6. LLM 元数据生成改为离线增强；
7. 版本管理增加发布日期、实施日期、废止日期、替代关系、状态来源；
8. 评估集必须前置；
9. 前置查询理解层：标准号/条款号解析归一化 + 领域同义词/自定义分词词典（§9.0）；
10. 状态 + 密级作为不可绕过的统一过滤，下推至 Milvus 与 PG（§9.6）；
11. 表格限值问答增加 cell 级结构化定位子流程（§9.7）；
12. 检索期增加一跳引用图扩展回填（§10.5）；
13. 拒答阈值在评估集上标定，上下文设 token 预算（§11.4 / §11.5）；
14. 增加局部修订/修改单的条款级版本流程（§13.3）；
15. 补充服务降级、延迟预算与 embedding 灰度迁移（§16.4 / §16.5）。
## 19. 推荐最终方案摘要

最终建议采用如下路线：

```text
第一阶段：
MinerU → PostgreSQL 结构化底座 → 文本路 Milvus → 三路召回 → RRF → DeepSeek 溯源回答

第二阶段：
加入 reranker、表格结构化检索、LLM 元数据增强、评估闭环

第三阶段：
针对扫描件和图表密集规范加入视觉路

第四阶段：
从页面级视觉召回升级到 block 级视觉召回

第五阶段：
实现 auto 路由和 both 模式融合
```

一句话概括：

> 系统应以 PostgreSQL 结构化底座为核心，以文本路为主召回路径，以视觉路作为扫描件、图表和复杂版式内容的补充，以严格的版本管理和条款级溯源作为规范 RAG 的底线。

## 20. 整合版结论

整合后的技术路线不是简单保留旧版或完全采用 v2，而是形成一个分层演进方案：

1. 旧版中“C++ 主程序 + Python 解析服务 + Milvus + PostgreSQL + DeepSeek”的工程骨架应保留；
2. 旧版中“C++ 内嵌 ONNX 跑模型”的主路线应弱化为轻量备选；
3. v2 中“大模型服务化”的方向应作为主路线；
4. v2 中“双路召回”的方向应保留，但不应第一阶段全量实现；
5. 文本路应作为默认主力；
6. 视觉路应作为增强能力后置上线；
7. both 模式必须经过评估验证后再开放；
8. 表格结构化、条款号原子性、版本状态、强制性条文、溯源生成，是本系统区别于普通 RAG 的核心。

最终架构应追求：

```text
可解析、可检索、可溯源、可评估、可更新、可扩展。
```
